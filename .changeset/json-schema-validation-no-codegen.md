---
'@mastra/schema-compat': patch
---

Fixed JSON Schema tool inputs failing validation in runtimes started with `--disallow-code-generation-from-strings`. The JSON Schema adapter now validates with `@cfworker/json-schema`, which never generates code, instead of Ajv, which compiles each schema with `new Function`. Most schemas validate as before: `format` is never checked, and OpenAPI `nullable: true` still allows `null` on every subschema, including one reached only by a `$ref` to another location such as `#/components/schemas/User`. A `nullable` target reached only through an absolute URI, or through a `#/` reference inside a subschema with its own `$id`, does not allow `null`, so such a value is refused where Ajv accepted it. Keywords beside a `$ref` still apply in every draft, and a `$ref` inside draft-07 `dependencies`, or pointing into it, resolves. Two behaviours change, described below: a schema containing `$dynamicRef` is refused, and `$recursiveRef` now resolves in every draft. Other differences from Ajv are listed after them. Error messages now use the new validator's wording, for example `5000 is greater than 500.` and `Instance has more than 1 properties.`, and an extra property under `additionalProperties: false` is reported once as `Property "x" does not match additional properties schema.`. Because the schema is interpreted rather than compiled, large values take longer to check: a valid 34 MB value with 800,000 rows took about 1.5 to 8 seconds, depending on the schema and the load, where Ajv took about 25 to 350 ms.

A schema with a `$dynamicRef` key anywhere is now refused, including where only a `$ref` or `dependencies` reaches it and inside literal data such as `const`, `enum`, `default` or `examples`: every value gets one issue saying `$dynamicRef is not supported`. The new validator cannot resolve `$dynamicRef`, and refusing the schema is safer than letting such references pass unchecked. `$ref` is unaffected. `$recursiveRef` is now resolved in every draft; Ajv resolved it only for some draft and anchor combinations.

Other differences from Ajv:

- `id`, the draft-04 identifier, is ignored, as Ajv ignored it; `$id` still applies.
- A schema Ajv refused as invalid is now used as written, and a malformed keyword is ignored. For example, `additionalProperties: "false"` (a string), draft-03 `required: true`, `nullable` without `type`, and an `enum` with repeated members no longer refuse every value. Fix such schemas at their source. An OpenAPI 3.0 or draft-04 boolean bound, `minimum: 5, exclusiveMinimum: true`, is read as `exclusiveMinimum: 5` (likewise for `maximum`), and elsewhere a boolean bound without a number beside it, or `false`, is ignored; Ajv refused every value against such a schema.
- A few values Ajv accepted are refused with a `Schema validation error`: an array item nested about 10,000 levels deep under `uniqueItems`, an object key holding a lone UTF-16 surrogate, a function, `bigint` or symbol under a subschema, any value under a `$ref` to a target named like a keyword (such as `#/components/schemas/properties`) that itself holds a `#/` reference, any value under a `$ref` to a definition outside a schema keyword that is named `id` (such as `#/components/schemas/id`), or is a boolean named `exclusiveMinimum` or `exclusiveMaximum` (those are dropped as the draft-04 identifier and boolean bounds), and any value against a schema in which a `$ref` (even in an unused definition) points at a name map or at literal data, such as `#/properties` or a `const` value, that holds a boolean `exclusiveMinimum` or `exclusiveMaximum`: read as a schema it would be a bound, read as a name map it is a property's schema. Otherwise such a target is left as written, so a `$ref` into a name map or into `const` sees `nullable`, `format` and `id` there unchanged.
- Every schema is validated with 2020-12 keywords, so `prefixItems`, `dependentRequired`, `minContains` and `unevaluated*` apply even without a `$schema`, and also under a draft-07 `$schema`, which Ajv read with draft-07 keywords only. For example, `[1, 'a']` now passes `prefixItems: [{ type: 'number' }]` with `items: { type: 'string' }`, `[]` passes `contains` with `minContains: 0`, and a property evaluated only by `if` satisfies `unevaluatedProperties: false`. An `unevaluatedProperties` or `unevaluatedItems` inside a subschema sees only what that subschema evaluates, as with Ajv; nested under `not`, or beside an `if`, it can still give a different result from Ajv in rare schemas.
- `multipleOf` compares decimals exactly, so `0.07` is a multiple of `0.01`; Ajv refused it through floating-point error. Values JSON cannot carry differ too: `NaN` is not refused by `minimum` or `maximum` and never counts as a duplicate under `uniqueItems`, and a property an object only inherits, such as a prototype getter, is not checked against `properties`.
- `anyOf` stops at the first branch that passes, as Ajv did, except in a schema that uses `unevaluatedProperties` or `unevaluatedItems`, where every branch is checked for the properties and items it evaluates. A schema that a `$ref` or `$recursiveRef` points to and that can refer back to itself is checked against each value at most twice per value location and mode, and its result is reused from then on, so a recursive schema whose `anyOf`, `oneOf`, `allOf` or `if` reaches the same child more than once takes time that grows with the size of the value, not exponentially with its depth, valid or not. Each object or array checked against such a schema keeps a marker of about 120 bytes until the validation ends; strings, numbers, booleans and `null` are not kept. When several keywords share a reused result, its errors are reported once. In a schema that uses `unevaluatedProperties` or `unevaluatedItems`, results are not reused, so a recursive union there can still take time exponential in its depth. A schema whose unions reach the same definition again without recursion can take time exponential in the schema's own nesting, as with Ajv, but tens to hundreds of times slower than Ajv there (a 22-level `allOf` chain: about 20 seconds, where Ajv took about 50 ms). An `anyOf` whose branch refers back to the same schema at the same value (`{ anyOf: [{ type: 'null' }, { $ref: '#' }] }`), a value that fails with about 100,000 errors, or a value nested about 200 levels deep under a recursive schema in a fresh process (the exact limit varies with the state of the process; Ajv accepted thousands of levels), ends in `Maximum call stack size exceeded`, so the value is refused; it is never accepted.

An object property whose value is `undefined` is handled as Ajv handled it, at any depth and on any object: it counts as absent for `properties`, `required`, `dependentRequired`, `dependentSchemas` and `dependencies`, also inside `if`, `anyOf` and the other combinators, and as present for `additionalProperties`, `unevaluatedProperties`, `patternProperties`, `propertyNames`, `minProperties` and `maxProperties`. So `{ extra: undefined }` is refused where `extra` is not allowed, and a declared property set to `undefined` passes. An `undefined` value checked by a subschema matches no `type`, and a root value of `undefined` passes `{}`, as with Ajv. This matters for model output: an OpenAI structured-output schema turns `null` into `undefined`, so an undeclared `null` key reaches validation as `undefined`.

`uniqueItems` now checks an array in one pass wherever the keyword appears, including behind a `$ref`, so its cost grows linearly with the array, objects and arrays included. Items compare by JSON equality: `"1"` and `1` differ, `1` and `1.0` are equal, and objects with the same members in a different order are equal. Only an object holding a value JSON cannot carry, such as `NaN` or a function, is still compared pair by pair, with other such objects.

The one-pass check, the `undefined` handling, the `anyOf` and `oneOf` evaluation, the reuse of subschema results, the `dependencies` lookup and the `maxProperties` message are a local patch of the third-party `@cfworker/json-schema` 4.1.6 (`patches/@cfworker__json-schema@4.1.6.patch`, listed under `patchedDependencies` in `pnpm-workspace.yaml`), which this package bundles into its build. The patch also resolves a `#/` reference the library misses by following its JSON Pointer, never checks `format`, keeps annotations only from subschemas that pass, and stops `not` and `if` at their first error. Apart from those, results and messages are the library's. The patch is pinned to 4.1.6: a different version makes `pnpm install` fail with `ERR_PNPM_UNUSED_PATCH` instead of silently dropping it. Drop the patch file and its `patchedDependencies` entry once `@cfworker/json-schema` covers these changes itself.

The validator is imported lazily when the package loads, because `@cfworker/json-schema` reads `self.location` on import and throws in a browser worker created from a blob URL. Importing the package therefore never fails there. Until the validator has loaded, which happens shortly after startup, and permanently where it cannot load (such as those blob workers), every JSON Schema validation fails closed with the issue `JSON Schema validator unavailable (<reason>)`; it never reports success. During that window a schema with `$dynamicRef` gets this issue too, not the `$dynamicRef` one. The new `jsonSchemaValidatorReady()` resolves once the import has settled, in every copy of the adapter loaded in the process, including copies bundled into other packages. A copy loaded later, such as one inside a package imported on demand, makes `jsonSchemaValidatorLoading()` true again until it has loaded, and its schemas fail closed as above meanwhile. `jsonSchemaValidatorLoading()` reports whether any copy is still loading. Before a synchronous `validate` call made right after startup, await `jsonSchemaValidatorReady()` while `jsonSchemaValidatorLoading()` is true. Where the validator cannot load, as in a worker created from a blob URL, validate in a worker started from a script URL or on the main thread instead.

```ts
import { jsonSchemaValidatorLoading, jsonSchemaValidatorReady, toStandardSchema } from '@mastra/schema-compat';

const schema = toStandardSchema({ type: 'object', properties: { id: { type: 'string' } } });
if (jsonSchemaValidatorLoading()) await jsonSchemaValidatorReady();
const result = schema['~standard'].validate({ id: 'a1' });
```
