'@mastra/schema-compat': patch
---

Fixed JSON Schema tool inputs failing validation in runtimes started with `--disallow-code-generation-from-strings`. The JSON Schema adapter now validates with `@cfworker/json-schema`, which never generates code, instead of Ajv, which compiles each schema with `new Function`. The adapter accepts only the keyword list described in the other `@mastra/schema-compat` entry of this release, and the differences below apply only to schemas within that list.

Most schemas validate as before: `format` is never checked, and OpenAPI `nullable: true` still allows `null` on every subschema, including one reached only by a `$ref` such as `#/$defs/User`. Keywords beside a `$ref` still apply in every draft. Error messages now use the new validator's wording, for example `5000 is greater than 500.` and `Instance has more than 1 properties.`, and an extra property under `additionalProperties: false` is reported once as `Property "x" does not match additional properties schema.`. Issue paths are unchanged. Because the schema is interpreted rather than compiled, large values take longer to check: a valid 34 MB value with 800,000 rows took about 1.5 to 8 seconds, depending on the schema and the load, where Ajv took about 25 to 350 ms.

`anyOf` stops at the first branch that passes, as Ajv did. A schema that a `$ref` points to and that can refer back to itself is checked against each value at most twice per value location and mode, and its result is reused from then on, so a recursive schema whose `anyOf`, `oneOf` or `allOf` reaches the same child more than once takes time that grows with the size of the value, not exponentially with its depth, valid or not. Each object or array checked against such a schema keeps a marker of about 120 bytes until the validation ends; strings, numbers, booleans and `null` are not kept. When several keywords share a reused result, its errors are reported once. A schema whose unions reach the same definition again without recursion can take time exponential in the schema's own nesting, as with Ajv, but tens to hundreds of times slower than Ajv there (a 22-level `allOf` chain: about 20 seconds, where Ajv took about 50 ms). A value that fails with about 100,000 errors, or a value nested about 200 levels deep under a recursive schema in a fresh process (the exact limit varies with the state of the process; Ajv accepted thousands of levels), ends in `Maximum call stack size exceeded`, so the value is refused; it is never accepted.

An object property whose value is `undefined` is handled as Ajv handled it, at any depth and on any object: it counts as absent for `properties`, `required` and `dependentRequired`, also inside `anyOf` and the other combinators, and as present for `additionalProperties`, `propertyNames`, `minProperties` and `maxProperties`. So `{ extra: undefined }` is refused where `extra` is not allowed, and a declared property set to `undefined` passes. An `undefined` value checked by a subschema matches no `type`, and a root value of `undefined` passes `{}`, as with Ajv. This matters for model output: an OpenAI structured-output schema turns `null` into `undefined`, so an undeclared `null` key reaches validation as `undefined`.

The one-pass `uniqueItems` check, the `undefined` handling, the `anyOf` and `oneOf` evaluation, the reuse of subschema results, the `dependencies` lookup and the `maxProperties` message are a local patch of the third-party `@cfworker/json-schema` 4.1.6 (`patches/@cfworker__json-schema@4.1.6.patch`, listed under `patchedDependencies` in `pnpm-workspace.yaml`), which this package bundles into its build. The patch also resolves a `#/` reference the library misses by following its JSON Pointer, never checks `format`, keeps annotations only from subschemas that pass, stops `not` and `if` at their first error, never reads `examples` as schemas, and ignores the draft-04 `id`. Some of these patched paths serve keywords the list now refuses; they stay in the patch so that it matches the library's structure. Apart from those, results and messages are the library's. The patch is pinned to 4.1.6: a different version makes `pnpm install` fail with `ERR_PNPM_UNUSED_PATCH` instead of silently dropping it. Drop the patch file and its `patchedDependencies` entry once `@cfworker/json-schema` covers these changes itself.

The validator is imported lazily when the package loads, because `@cfworker/json-schema` reads `self.location` on import and throws in a browser worker created from a blob URL. Importing the package therefore never fails there. Until the validator has loaded, which happens shortly after startup, and permanently where it cannot load (such as those blob workers), every JSON Schema validation fails closed with the issue `JSON Schema validator unavailable (<reason>)`; it never reports success. During that window a schema outside the keyword list gets this issue too, not the refusal. The new `jsonSchemaValidatorReady()` resolves once the import has settled, in every copy of the adapter loaded in the process, including copies bundled into other packages. A copy loaded later, such as one inside a package imported on demand, makes `jsonSchemaValidatorLoading()` true again until it has loaded, and its schemas fail closed as above meanwhile. `jsonSchemaValidatorLoading()` reports whether any copy is still loading. Before a synchronous `validate` call made right after startup, await `jsonSchemaValidatorReady()` while `jsonSchemaValidatorLoading()` is true. Where the validator cannot load, as in a worker created from a blob URL, validate in a worker started from a script URL or on the main thread instead.

```ts
import { jsonSchemaValidatorLoading, jsonSchemaValidatorReady, toStandardSchema } from '@mastra/schema-compat';

const schema = toStandardSchema({ type: 'object', properties: { id: { type: 'string' } } });
if (jsonSchemaValidatorLoading()) await jsonSchemaValidatorReady();
const result = schema['~standard'].validate({ id: 'a1' });
```
