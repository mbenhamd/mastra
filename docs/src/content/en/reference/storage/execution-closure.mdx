# Execution closure

An execution closure is a fenced, versioned export of one harness session subtree: a root session and every descendant reached through `parent_session_id`, plus the memory, observational-memory, workflow, and terminal-handoff rows that belong to it. Export and import are implemented by `PostgresStore` and are intended for migration and disaster recovery, not routine replication.

The unit is "fenced" because it separates durable state and evidence from live execution authority:

- **`state` rows** (sessions, threads, messages, snapshots, terminalizations) keep their persisted content, except that live authority is stripped: session `owner_id`/`lease_expires_at` and terminalization `owner_id`/`claim_token`/`lease_expires_at` are cleared, while the terminalization's positive `claim_generation` is preserved as the fencing counter a new claimant increments. A pending workflow snapshot handoff is materialized as canonical snapshot state rather than restored as a live fence.
- **`fence` rows** (tombstones, terminal intents and admissions, projection fences, channel action receipts, destination receipts) are restored as evidence, rebound to the destination session incarnation, and have stale claims/leases cleared so an old in-flight callback cannot revive; claimed terminal intents are requeued to `pending` so a destination worker can claim them.
- **`authority` rows** (wakeups, outbox/inbox, channel bindings, action tokens, thread-delete fences, attachment operations, projection intents, workflow snapshot handoffs, pressure counters) are exported for completeness but never restored; pending session-record projection work is instead restaged deterministically from the imported session rows, and terminal/projection pressure counters are rebuilt from the live rows actually restored.
- **`shared-resource` rows** are restored only when absent, so an archive cannot overwrite a live shared row.

Every imported session row receives a `session_incarnation` minted or adopted at the destination, so source-era grants, leases, and callbacks are fenced by the runtime rather than replayed.

## Usage

```typescript
import { PostgresStore } from '@mastra/pg'

const source = new PostgresStore({ id: 'source', connectionString: SOURCE_URL })
const destination = new PostgresStore({ id: 'dest', connectionString: DEST_URL })

const payload = await source.exportExecutionClosure({
  harnessName: 'default',
  sessionId: 'session-to-migrate',
})

const result = await destination.importExecutionClosure(payload)
// result.status === 'imported' | 'pinned'
```

Export runs under a single `REPEATABLE READ` transaction, so the closure is a consistent snapshot; import runs inside one transaction, so a failure writes nothing and a lost acknowledgement can simply re-import.

## `exportExecutionClosure(key)`

Exports the session subtree rooted at `key.sessionId` in the `key.harnessName` namespace.

Returns: `Promise<ExecutionClosurePayload>` — `{ manifest, rows }`. `manifest` records the format version, closure key, provenance, sorted `sessionIds`, per-session `incarnations` captured at export, scoped `threadIds`/`runIds`/`resourceIds`, a `sha256:` digest for every registered closure table, `completeness`, and `pins`.

When the exporter cannot prove the unit is complete — for example the root session's parent lies outside the subtree, a session references a missing thread, or attachment bytes are owned externally — it still exports but records `completeness: 'pinned'` and the reasons in `pins`.

Throws a `MastraError` when the root session does not exist.

## `importExecutionClosure(payload)`

Verifies the payload against its manifest before staging a single row, then applies it in one transaction.

Verification fails closed on: unsupported manifest format/version, unknown or missing registered tables, duplicate table entries, row-count or digest mismatches, `sessionIds` inconsistent with the exported session rows, rows carrying a foreign `harness_name`, and payload row columns outside each table's registered schema.

On apply:

- A session row that already exists must match the imported row (except `session_incarnation`) — or be that same session legitimately advanced by destination workers at a strictly newer `version` with identical creation identity; the persisted incarnation is reused — including after a concurrent import — so `result.incarnations` always reflects the value actually stored.
- Any other `state`/`fence` row that already exists must equal the imported row canonically, or differ only in the lifecycle columns a destination worker advances (claim/ack/settle fields, applied projection intents, receipt delivery state). Anything else aborts the transaction with `DESTINATION_ROW_CONFLICT` instead of silently merging a foreign row.
- `authority` rows are counted in `skipped` and never inserted.
- Imported terminal intents lose stale claim fields and are requeued to `pending`; workflow handoff fences are materialized as snapshot evidence rather than restored; pending session-record projection work is restaged deterministically; terminal/projection pressure counters are rebuilt from the restored live rows.

Returns: `Promise<ExecutionClosureImportResult>` — `{ status, incarnations, inserted, skipped, pins }`. `status` is `'imported'` for a complete unit or `'pinned'` when the manifest recorded pins; `inserted`/`skipped` count rows written and rows already present (or never restored) per table.

Re-importing the same payload converges while the destination has not diverged the imported rows: rows already present are skipped, nothing duplicates, and the returned incarnations are the ones persisted by the first import. Convergence also holds when a destination worker merely advanced an imported row through its normal lifecycle — claiming or settling a terminal intent, applying a restaged projection intent, or saving the session at a newer version. A `DESTINATION_ROW_CONFLICT` after a successful first import means the unit is already present and the destination row has since diverged in a way that is not a valid lifecycle successor — the import aborts rather than overwriting foreign data.

## Availability

`exportExecutionClosure`/`importExecutionClosure` are `PostgresStore` methods on `@mastra/pg`. The manifest, registry, and payload types are exported from `@mastra/core/storage`. Tables belonging to disabled storage domains are tolerated as absent only when they carry zero rows; a payload that contains rows for a missing table fails with `MISSING_TABLE`.
