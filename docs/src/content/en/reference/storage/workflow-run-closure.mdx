# Workflow run closure

A workflow run's closure is every row workflow storage keeps for one `(workflowName, runId)` pair:

- its snapshot;
- its snapshot handoff, released or not;
- its terminal rows: journal, effects, terminal snapshot, destination receipts, continuation plans and recovery ancestry.

`deleteWorkflowRunClosure` erases one settled run's closure in a single atomic step. `listWorkflowRunClosuresByResource` finds the runs to erase for a resource. Together they let an application erase a user's workflow data, for example for account deletion.

## Usage

```typescript
const workflows = await storage.getStore('workflows')

if (workflows?.getWorkflowSnapshotHandoffCapabilities().closureDeleteVersion !== 1) {
  throw new Error('This store cannot erase workflow run closures')
}

let after
do {
  const page = await workflows.listWorkflowRunClosuresByResource({ resourceId, after, limit: 100 })
  if (page.status !== 'listed') throw new Error('Closure listing is unsupported')

  for (const { workflowName, runId } of page.closures) {
    const result = await workflows.deleteWorkflowRunClosure({
      workflowName,
      runId,
      expectedResourceId: resourceId,
    })
    // 'deleted' and 'missing' are done. Retry 'fenced' and 'active' later.
    // 'resource_mismatch' is a refusal.
  }
  after = page.nextCursor
} while (after)
```

## `deleteWorkflowRunClosure(input)`

Erases one run's closure.

Input: `{ workflowName, runId, expectedResourceId }`.

Returns: `Promise<DeleteWorkflowRunClosureResult>`. The checks run in this order, and nothing changes unless the result is `deleted`:

- `missing`: storage holds no row for the run. Repeating a delete answers `missing`.
- `resource_mismatch`: the snapshot, handoff or terminal snapshot records another resource, or none at all.
- `fenced`: the handoff is pending and not released, so its owner is still writing the run. A completed handoff doesn't block erasure, released or not.
- `active`: one of these holds, and you can retry later:
  - the snapshot status isn't settled (`success`, `failed`, `canceled`, `tripwire`, `bailed` or `skipped`);
  - a terminalization owner holds a live lease on the journal;
  - a nested child run hasn't completed its terminal journal. Erase child runs before their parents.
- `deleted`: the closure is gone. `removed` reports `{ snapshot, handoff, terminalRows }`.
- `unsupported`: the store doesn't implement closure erasure.

The run's content-free parent revision is kept as the run-id reuse fence, with the erased run's terminal status cleared so a reused run id can run again. Late writers from the erased run change nothing:

- A delayed `releaseWorkflowSnapshotHandoff` answers `missing` while the run has no handoff. Once the same run id is used again, its next handoff claim starts above the erased claims, so the delayed release answers `conflict`.
- A delayed terminal recovery-ancestry write answers `missing_run` until the run id is used again.

## `cancelWorkflowRunForErasure(input)`

Settles a run that will never settle on its own, so its closure can be erased. For example, an erased account's agent loop may be suspended on a question, or a run's execution may have stopped. It overwrites the unsettled snapshot in place with an empty `canceled` snapshot under the same resource. The row stays, and a later `deleteWorkflowRunClosure` erases the closure.

Input: `{ workflowName, runId, expectedResourceId }`.

Returns: `Promise<CancelWorkflowRunForErasureResult>`. All checks and the write happen in one atomic step, under the same locks as `deleteWorkflowRunClosure`. A journal or nested child can't appear between a check and the write. The checks run in this order. Snapshot content changes only when the result is `cancelled`:

- `missing`: storage holds no snapshot for the run.
- `resource_mismatch`: the snapshot, handoff or terminal snapshot records another resource, or the snapshot records none.
- `fenced`: an unreleased handoff, pending or completed, fences the run's snapshot writes. This is the same fence `persistWorkflowSnapshot` enforces.
- `journaled`: the run has a terminalization journal, in any phase. Its owner settles the run, so the run is never overwritten.
- `active`: retry later. Either a nested child run hasn't completed its terminal journal, or the run's parent revision latched a terminal status that its snapshot doesn't show yet. The nested child can be linked by a parent effect or by recovery ancestry, whatever its resource.
- `settled`: the snapshot status is already settled and remains unchanged.
- `cancelled`: the snapshot is now an empty `canceled` snapshot. The parent revision moved, and latched `canceled`, as for any snapshot write.
- `unsupported`: the store doesn't implement the erasure cancel.

A nested child admitted after the cancel finds its parent terminal and is refused.

:::warning

The store has no executor lease or liveness check. It cancels a `running` run that lacks a journal, an unreleased handoff and a pending nested child, even while an executor in another process still runs it. That executor's next generation-guarded persist then fails as stale, and its work is discarded. An `active` result reports a settlement or a nested child in flight. It says nothing about running executors. Call `cancelWorkflowRunForErasure` only for runs that will never settle on their own, whose owner is gone and for which no executor can be admitted.

:::

In the in-memory store, both `cancelled` and `settled` protect the selected run from writes that would reopen it. A `settled` selection keeps the stored snapshot and records its checked status as data. Later writes to the run are stored as plain data:

- `persistWorkflowSnapshot`, `updateWorkflowState`, `updateWorkflowResults`, and resume admission, rollback and finalization throw `WorkflowStaleSnapshotPersistError` when the new status disagrees with the run's terminal status. Writes with the same status still succeed.
- `bindWorkflowNestedRunOwnership` always returns `{ status: 'missing_run' }`, whatever status the snapshot would keep, so no new nested child starts on the run. The PostgreSQL store also returns `missing_run` for a run with a latched terminal status.
- `persistWorkflowStepUpdate` doesn't throw. It returns `{ status: 'finalized', disposition }`, as it does for any terminal run.
- An already settled run keeps its snapshot content.
- Closure deletion removes this protection before the same run ID is used again.
- Runs not selected for erasure keep their existing write behavior.

The in-memory store also lets an ordinary write reopen a settled run, which the PostgreSQL store refuses. The erasure cancel treats such a reopened run, with no journal and no pending nested child, as unsettled and cancels it.

## `listWorkflowRunClosuresByResource(input)`

Pages the runs that hold rows recorded under a resource.

Input: `{ resourceId, after?, limit }`. `limit` is required and between 1 and 100. `after` is the `nextCursor` of the previous page.

Returns: `Promise<ListWorkflowRunClosuresByResourceResult>`:

- `{ status: 'listed', closures, hasMore, nextCursor? }`: each entry is `{ workflowName, runId, snapshot, terminalSnapshot, handoff? }`. The flags say which rows matched the resource, and `handoff` is `{ status, released }`. Released handoffs are included, so a delivered handoff whose snapshot was already deleted is still found. Runs are ordered by `(workflowName, runId)` in code-point order.
- `{ status: 'unsupported' }`: the store can't list closures. It never answers an empty page instead.

## `listWorkflowRunsByThreadForErasure(input)`

Pages a resource's runs that hold a copy of a thread's data, in any run status. It reads every row `deleteWorkflowRunClosure` erases that can hold such a copy: the canonical snapshot, the handoff snapshot (kept after a `deleteRun` release removes the canonical snapshot) and the terminal recovery envelope. Use it to erase a thread or a session inside a resource that stays. The `threadId` filter of `listWorkflowRuns` reads a single value, so it misses an agent loop snapshot that's still `pending` or `running`, and a run whose first suspended step names another thread.

Input: `{ resourceId, threadId, after?, limit, includeUnattributed? }`. `limit` is required and between 1 and 100. `after` is the `nextCursor` of the previous page.

A snapshot (canonical or handoff) matches when one of these places records the thread id:

- any `memoryInfo.threadId`, at any depth, such as an agent loop step's `suspendPayload.__streamState.messageList.memoryInfo` (any step, any status) or the durable loop's `context.input.messageListState.memoryInfo`;
- the durable loop's `context.input.state.threadId`;
- the request context stored with every started run: `requestContext.MastraMemory.thread.id` or `requestContext.mastra__threadId`.

A terminal envelope matches on any `memoryInfo.threadId` or on its `requestContextPatch` (`MastraMemory.thread.id`, `mastra__threadId`).

Returns: `Promise<ListWorkflowRunsByThreadForErasureResult>`:

- `{ status: 'listed', runs, hasMore, nextCursor? }`: runs are ordered by `(workflowName, runId)` in code-point order. A matching run is `{ workflowName, runId, attribution: 'thread', rows }`, where `rows` is `{ snapshot, handoff, terminalSnapshot }` and says which of those rows the run has under the resource.
- `{ status: 'unsupported' }`: the store can't answer. It never answers an empty page instead.

The `pending` snapshot that `createRun` stores before a run starts records no thread. With `includeUnattributed: true`, the listing also returns the resource's runs that have a canonical snapshot and record no thread id in any row, as `{ workflowName, runId, attribution: 'unattributed', rows, status?, createdAt, updatedAt, contentFree }`. `status`, `createdAt` and `updatedAt` come from the canonical snapshot row. `contentFree` is true only when all of these hold:

- the run has no handoff and no terminal snapshot row under the resource;
- `context` is absent, `null` or `{}`, or its only key is `input` and that input is `null` or `{}`;
- `requestContext` is absent, `null` or `{}`.

A nested run's `pending` snapshot whose `context.input` holds the parent step's payload isn't content-free. An unattributed run may belong to another thread's turn that's still starting, so don't erase it as the thread's run without other evidence, such as its age. The listing itself never changes anything.

## Availability

The in-memory store and `@mastra/pg` report `closureDeleteVersion: 1`, `closureCancelVersion: 1` and `threadErasureListVersion: 1` from `getWorkflowSnapshotHandoffCapabilities()`. Other stores answer `unsupported`. The input and result types are exported from `@mastra/core/storage`.

On PostgreSQL, the listing uses resource indexes on the snapshot, handoff and terminal snapshot tables, and the reuse fence uses the `handoff_claim_generation_hwm` column of `mastra_workflow_parent_revisions`. `init()` creates them. With an externally managed schema (`disableInit`), apply the statements from `exportSchemas()` before deploying. The `@mastra/pg` changelog lists them.
