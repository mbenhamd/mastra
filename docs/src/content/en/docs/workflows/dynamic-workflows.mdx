# Dynamic workflows

:::beta

Breaking changes may occur without a major version bump until the API is stable.

:::

Dynamic workflows are workflow definitions expressed as data instead of code. A definition is a JSON document that describes the workflow's schemas and step graph. Mastra validates the definition and registers it as a runnable workflow, then persists it in storage so it survives process restarts.

Because a definition contains no JavaScript closures, anything that produces JSON can author a workflow. Sources include an HTTP client or LLM. A visual editor or your own tooling can also produce the definition. Once registered, a dynamic workflow runs through the same execution API as a code-defined workflow.

## When to use dynamic workflows

Use dynamic workflows when users, agents, visual editors, or external systems need to create workflows without changing application code or deploying again.

Keep defining workflows with [`createWorkflow()`](/docs/workflows/overview) when the workflow belongs in your application source or needs custom step functions. Dynamic workflows can invoke agents, tools, and workflows that are already registered on the `Mastra` instance.

## Quickstart

The following example registers a tool and invokes it from a dynamic workflow. It then runs the workflow. `LibSQLStore` persists the definition in `mastra.db`, so Mastra can restore it after a restart.

```typescript title="src/dynamic-workflow.ts"
import { Mastra } from '@mastra/core/mastra'
import { createTool } from '@mastra/core/tools'
import { LibSQLStore } from '@mastra/libsql'
import { z } from 'zod'

const greetingTool = createTool({
  id: 'create-greeting',
  description: 'Create a greeting for a name',
  inputSchema: z.object({
    name: z.string(),
  }),
  outputSchema: z.object({
    message: z.string(),
  }),
  execute: async ({ name }) => ({
    message: `Hello, ${name}!`,
  }),
})

const mastra = new Mastra({
  storage: new LibSQLStore({
    id: 'mastra-storage',
    url: 'file:./mastra.db',
  }),
  tools: { 'create-greeting': greetingTool },
})

await mastra.addDynamicWorkflow({
  id: 'greeting-workflow',
  description: 'Create a greeting for the supplied name',
  inputSchema: {
    type: 'object',
    properties: {
      name: { type: 'string' },
    },
    required: ['name'],
  },
  outputSchema: {
    type: 'object',
    properties: {
      message: { type: 'string' },
    },
    required: ['message'],
  },
  graph: [
    {
      type: 'tool',
      id: 'greet',
      toolId: 'create-greeting',
    },
  ],
})

const workflow = mastra.getWorkflow('greeting-workflow')
const run = await workflow.createRun()
const result = await run.start({
  inputData: { name: 'Ada' },
})

if (result.status === 'success') {
  console.log(result.result.message)
}
```

The workflow prints `Hello, Ada!`. Calling [`addDynamicWorkflow()`](/reference/core/addDynamicWorkflow) validates the definition before it changes storage or the live workflow registry.

The definition uses JSON Schema because it must survive a JSON round trip. The `graph` describes which registered components to invoke and how data moves between them. See the [dynamic workflow definition reference](/reference/workflows/dynamic-workflow-definition) for every field and graph entry.

## Use the admitted schema dialect

Mastra accepts a bounded JSON Schema Draft 2020-12 subset for dynamic workflow schemas. Historical draft-07 `$schema` URIs are accepted as aliases, but draft-07-only keywords aren't. Mastra rejects a definition before persistence when a schema uses an unknown keyword or a constraint that it can't convert to an equivalent Zod validator. Validation errors include the schema field and a JSON Pointer to the rejected keyword.

Both `inputSchema` and `outputSchema` are required. Optional state, request-context, and agent output schemas use the same contract when present. The subset supports typed objects, homogeneous arrays, exact-length closed tuples, primitive constraints, primitive `enum` and `const` values, nullable type arrays, and the `uuid` string format. Composition keywords such as `$ref`, `oneOf`, and `allOf` aren't admitted.

The [dynamic workflow definition reference](/reference/workflows/dynamic-workflow-definition#admitted-json-schema) lists every admitted keyword, tuple rule, format, and size limit.

## Build and update definitions

A definition can come from any source that produces JSON. For example, an API route can accept a definition created by a visual editor and register it directly:

```typescript
const definition = await request.json()
await mastra.addDynamicWorkflow(definition)
```

### Register dependencies first

Register referenced components on the same `Mastra` instance before adding the dynamic workflow. Agent and nested workflow entries use their intrinsic IDs. A tool entry uses its key from the `Mastra` `tools` object, so the quickstart registers the tool under `create-greeting` before referencing that key with `toolId`.

Use a `mapping` entry when one step's output doesn't match the next step's input. Mapping entries can read data from the workflow input and previous step results, along with workflow state and request context. The [definition reference](/reference/workflows/dynamic-workflow-definition#mapping-steps) lists the supported mapping descriptors.

### Replace a workflow

Add a new definition with the same `id` to replace the persisted definition and live registration:

```typescript
await mastra.addDynamicWorkflow(updatedDefinition)
```

Calls that resolve the workflow after replacement use the updated registration. Mastra doesn't guarantee that an already-started, suspended, or evented run continues with the original graph, because durable execution can resolve later events by workflow ID. When an existing run must keep its original definition, use a new versioned workflow ID or drain and coordinate active runs.

### Add nested workflows together

When a root workflow references helper workflows that aren't registered yet, add the full set with [`addDynamicWorkflows()`](/reference/core/addDynamicWorkflows):

```typescript
await mastra.addDynamicWorkflows([rootDefinition, helperDefinition])
```

Mastra validates the bundle as a unit and determines the registration order from the dependencies. If validation fails, none of the definitions are registered.

### Manage definitions over HTTP

Applications don't need direct access to the `Mastra` instance to manage dynamic workflows. Use one of these interfaces:

- [Client SDK workflows API](/reference/client-js/workflows): Call `upsertDynamicWorkflow()` from a JavaScript or TypeScript client.
- [Server routes](/reference/server/routes): Send definitions to `POST /api/dynamic/workflows`.

On authenticated servers, dynamic-workflow management requires the `dynamic-workflows:read` and `dynamic-workflows:write` permissions. Running the registered workflow requires `workflows:execute`.

### Persist definitions

Stored definitions use the `workflowDefinitions` storage domain. On startup, Mastra loads active definitions from storage and registers them in dependency order.

An active historical definition that no longer satisfies the admitted schema contract is quarantined. Mastra continues loading unrelated workflows, but it doesn't register or execute the quarantined workflow. A workflow that depends on a quarantined workflow is also quarantined.

Inspect these rows with [`listQuarantinedDynamicWorkflows()`](/reference/core/listQuarantinedDynamicWorkflows):

```typescript
for (const workflow of mastra.listQuarantinedDynamicWorkflows()) {
  console.log(workflow.id, workflow.issues)
}
```

Each issue identifies the definition field, JSON Pointer, keyword, and reason. Replace the definition with an admitted schema under the same ID to clear its quarantine entry, or delete the stored definition through the dynamic-workflow management API.

Without a storage adapter that supports this domain, `addDynamicWorkflow()` still registers the workflow in memory, but the definition is lost when the process restarts. See the [storage reference](/reference/storage/overview) for adapter support.
