# PubSub

Mastra uses a publish/subscribe (pub/sub) system as its internal event bus. Components publish events to topics, and other components subscribe to those topics to react. The backend you configure decides how far those events travel: within one process or across processes on one host, or alternatively across separate instances.

Set the backend once on the `Mastra` instance for use throughout the system. The default is an in-process backend that requires no setup.

## How Mastra uses PubSub

Several built-in systems publish and subscribe to events through the same pub/sub bus:

- **Workflow execution**: The scheduler publishes a `workflow.start` event, and a long-lived worker consumes it to run the workflow. Step and lifecycle events flow over pub/sub during execution.
- **Scheduled workflows**: The scheduler dispatches due runs by publishing to the workflow topic. See [Scheduled workflows](/docs/workflows/scheduled-workflows).
- **Background tasks**: A task manager dispatches work to a worker group and fans task lifecycle updates out to subscribers, which is how background task streams stay live. See [Background task streaming](/docs/harness/background-tasks#subscribe-to-all-task-events).
- **Agent signals**: Sending a signal to an active agent run publishes an event on a thread topic, so a run executing in another process receives the signal.
- **Resumable streams**: Stream chunks are published per run, so a client that reconnects can replay what it missed.

Because these systems run on one bus, the backend you choose applies to all of them at once.

## Delivery modes

Backends deliver events in one of two modes, defined by the [`PubSub`](/reference/pubsub/base) contract:

- **Pull**: Consumers read from the backend on their own, which Mastra does with a long-lived worker loop. Distributed backends such as [`RedisStreamsPubSub`](/reference/pubsub/redis-streams) use this mode.
- **Push**: Events arrive without the consumer asking, either in process or over HTTP. The default [`EventEmitterPubSub`](/reference/pubsub/event-emitter) delivers this way in process.

Subscribers can also distribute work through consumer groups. Members of the same group split the events so each event is handled once. A subscriber without a group receives every event, which fans the stream out to all ungrouped subscribers.

## Default backend

When you don't set the `pubsub` option, Mastra uses [`EventEmitterPubSub`](/reference/pubsub/event-emitter). It delivers events in process using a Node.js [`EventEmitter`](https://nodejs.org/api/events.html#class-eventemitter), so it works without any external service.

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'

// No pubsub option: Mastra uses EventEmitterPubSub
export const mastra = new Mastra({})
```

Because it runs in process, events aren't persisted and don't reach other processes. The default suits a single instance, which covers most applications.

## Choosing a backend

Set the `pubsub` option on the `Mastra` instance to choose a backend. Each backend implements the same [`PubSub`](/reference/pubsub/base) contract, so the rest of your application doesn't change.

The deciding question is where the subscriber runs.

| Backend | Scope | Mode | Package |
| - | - | - | - |
| [`EventEmitterPubSub`](/reference/pubsub/event-emitter) | Single process | Pull and push | `@mastra/core` |
| [`UnixSocketPubSub`](/reference/pubsub/unix-socket-pubsub) | Multiple processes, one host | Push | `@mastra/core` |
| [`RedisStreamsPubSub`](/reference/pubsub/redis-streams) | Distributed, multiple hosts | Pull | `@mastra/redis-streams` |
| [`GoogleCloudPubSub`](/reference/pubsub/google-cloud-pubsub) | Distributed, multiple hosts | Pull | `@mastra/google-cloud-pubsub` |

### Multiple processes on one host

Use [`UnixSocketPubSub`](/reference/pubsub/unix-socket-pubsub) when several processes on the same machine need to share a stream. It delivers events over a Unix domain socket and elects one process as a broker. If the broker exits, the remaining processes elect a new one.

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { UnixSocketPubSub } from '@mastra/core/events'

export const mastra = new Mastra({
  pubsub: new UnixSocketPubSub('/tmp/mastra/events.sock'),
})
```

### Distributed deployments

Use a distributed backend when you run more than one instance or host, so every instance receives the same events. This matters whenever a request handled by one instance must reach work running on another.

For example, sending a signal to an agent run requires the signal event to cross the process boundary to the instance that owns the run. With the in-process default, that instance never receives the event.

Both backends below deliver across processes and hosts and persist events for redelivery.

### Workflow retry ownership

The pub/sub backend owns workflow-event delivery identity and, when supported, the `deliveryAttempt` count. Mastra may execute the source workflow event while that count is within its bounded budget. After the budget is exhausted, later deliveries only retry terminal failure propagation instead of running the source event again.

This constraint keeps the budget stable when another worker claims the event or the receiving process restarts, but backends without a tracked positive attempt value can't provide this cross-process guarantee.

If terminal failure publication is temporarily unavailable, or a configured workflow store can't yet observe the durable run snapshot, Mastra calls `nack` and leaves the source event with the backend. A missing snapshot in a configured store isn't treated as proof that the event is stale. When workflow storage isn't configured, Mastra publishes the terminal failure without this stale-state guard. A `workflow.fail` event never publishes another `workflow.fail`; failure processing retries the existing terminal event instead.

This is an at-least-once transport contract. Broker-owned attempts prevent a fresh source budget, but they don't make parent or finish notifications exactly once. Those effects need stable logical keys and idempotent consumers; a journal can make terminalization state durable, while a retained source event or outbox payload is required to retry the effect. Neither can retract an effect that was already delivered.

### Terminalization journal capability

The workflows storage contract includes an optional, fenced terminalization-journal capability for runtimes that coordinate a terminal workflow outcome across workers. `InMemoryStore` implements it for single-process development and `PostgresStore` implements it with an isolated `mastra_workflow_terminalizations` table. Other adapters report `unsupported` until they implement equivalent atomic operations.

The PostgreSQL journal is separate from the replaceable workflow snapshot. A snapshot rewrite or normal run deletion therefore can't erase an active claim or completed deduplication evidence. Successful acquisition and renewal return an opaque token and a monotonically increasing generation. A worker must present both values to renew, advance, or release the claim. Reads and unsuccessful operations redact all active fencing credentials so another worker can't impersonate the owner. An expired takeover receives a new token and generation and permanently fences the stale worker from later journal updates. PostgreSQL evaluates lease expiry with database time, and leases are limited to 24 hours.

The journal reserves this phase graph for root and nested terminalization:

```text
terminalization_pending
  -> run_state_persisted
  -> [parent_outbox_pending -> parent_effect_recorded]
  -> finish_outbox_pending
  -> finish_effect_recorded
  -> complete
```

The bracketed parent path is skipped for a root workflow. The journal reserves one first-terminal-wins slot per workflow run, so a competing success, failure, or cancellation returns `terminal_conflict` instead of starting another terminalization.

`persistWorkflowTerminalState` is the only operation that can enter `run_state_persisted`. It replaces the canonical workflow snapshot and advances the journal in one in-memory critical section or PostgreSQL transaction, so the phase can't certify a snapshot that was never written. The canonical snapshot remains replaceable. A later producer-outbox capability must retain immutable recovery evidence before source acknowledgment. Generic phase advancement can't enter snapshot, outbox, or effect-evidence phases. Each evidence-producing capability owns its atomic transition.

This storage capability is an adapter primitive, so configuring a supporting store doesn't by itself change workflow-event execution. A runtime consuming it must fail visibly when durable mode is requested with an unsupported adapter and keep the original event or a durable outbox payload available for recovery. It must also use a stable idempotency key for every external effect and acknowledge the source event only after `complete`. The journal provides no effect-payload storage or exactly-once delivery guarantee.

Completed records deliberately survive normal workflow-run deletion. Delete them only after a retention horizon longer than every broker redelivery and reclaim window. Deleting deduplication evidence earlier allows a sufficiently late delivery to acquire the run again.

The following example uses [Redis Streams](https://redis.io/docs/latest/develop/data-types/streams/):

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { RedisStreamsPubSub } from '@mastra/redis-streams'

export const mastra = new Mastra({
  pubsub: new RedisStreamsPubSub({
    url: 'redis://localhost:6379',
  }),
})
```

The following example uses [Google Cloud Pub/Sub](https://cloud.google.com/pubsub/docs):

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { GoogleCloudPubSub } from '@mastra/google-cloud-pubsub'

export const mastra = new Mastra({
  pubsub: new GoogleCloudPubSub({
    projectId: 'my-project',
  }),
})
```

## Resumable streams

Resumable streams let a client reconnect and replay events it missed, which requires the backend to keep recent history. Distributed backends such as [`RedisStreamsPubSub`](/reference/pubsub/redis-streams) persist events, so they support replay on their own.

In-process delivery doesn't keep history. To add replay on top of [`EventEmitterPubSub`](/reference/pubsub/event-emitter), wrap it in [`CachingPubSub`](/reference/pubsub/caching-pubsub), which records published events per topic so a late or reconnecting subscriber can catch up before continuing with live events.

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { CachingPubSub, EventEmitterPubSub } from '@mastra/core/events'
import { InMemoryServerCache } from '@mastra/core/cache'

const cache = new InMemoryServerCache()

export const mastra = new Mastra({
  pubsub: new CachingPubSub(new EventEmitterPubSub(), cache),
})
```

Visit the [PubSub reference](/reference/pubsub/base) for the full delivery contract and the configuration options for each backend.
